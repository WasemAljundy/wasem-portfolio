# Portfolio Storytelling

## Purpose
Make each project prove engineering judgment, ownership, and impact rather than merely listing technologies.

## Trigger
Use when selecting projects, writing case studies, homepage project summaries, experience sections, achievements, role descriptions, or resume-adjacent content.

## Core Narrative
A strong project story answers: Context -> Problem -> Constraints -> My Role -> Decisions -> Execution -> Quality/Trade-offs -> Outcome -> What I learned or enabled.

## Evidence Rules
Use only facts supported by the user's materials or explicit statements. Never invent metrics, team size, revenue, user counts, employer relationships, ownership, deployment status, or technical decisions. If impact cannot be quantified, describe qualitative outcomes precisely.

## Seniority Signals
Highlight scope, ownership, architecture, trade-offs, reliability, maintainability, testing, performance, release responsibility, stakeholder communication, and cross-functional judgment when supported. Avoid repeatedly saying “senior”; demonstrate it through decisions.

## Private Client / NDA
Explain the problem class, role, architecture or methods, and safe outcomes without naming protected clients, exposing credentials, proprietary screenshots, confidential metrics, or unique business details. Clearly label status.

## Case Study Template
- Hero: project, one-line value, status, role, timeframe.
- Snapshot: challenge, contribution, stack.
- Context and constraints.
- Key engineering decisions.
- Selected implementation highlights.
- Quality and validation.
- Outcome.
- Gallery or sanitized visuals.
- Links when public.

## Writing Style
Human, precise, calm, technical where useful, no inflated adjectives, no generic “passionate developer” language, no walls of buzzwords. Prefer specific verbs and concrete decisions.

## Definition of Done
A recruiter can understand value quickly, an engineer can see technical judgment, confidential boundaries are respected, and every claim is defensible.
